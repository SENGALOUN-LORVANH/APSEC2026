it may only handle the specific inputs those tests exercise.

that only makes the existing failing tests pass. Base every expected value on the documented or evidently
intended behaviour of the code (method contracts, Javadoc, names, surrounding logic, and the failing tests),
not on what the candidate patch happens to do.

Target, where meaningful for this bug:
- boundary values and values adjacent to those in the failing tests
- alternative branches and inputs the failing tests do not cover
- null or empty inputs when the API allows them
- exception behaviour and error conditions
- state changes and interactions between calls
- hard-coded constants, over-specific conditional guards, or early returns introduced by the patch
- functionality the patch removes or bypasses

Requirements for every test:
- complete, compilable Java source for one test class, no placeholders or pseudocode
- package declaration `{test_package}` and the imports it needs
- {junit_style}
- only public or package-visible API of the project; no reflection on private members
- deterministic: no randomness, time, network, or file-system dependence
- each test method finishes in well under 10 seconds
