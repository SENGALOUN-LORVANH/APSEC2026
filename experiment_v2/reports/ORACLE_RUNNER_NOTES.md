## Serious bug found and fixed
`defects4j export -p cp.test -w <dir>` bakes **absolute paths** into the returned classpath, pointing at that
specific checkout's own compiled classes. The first version of `validate_one_test` exported `cp.test` once
(from the *fixed* scratch copy) and reused it for the buggy and candidate runs too. Reusing fixed's classpath
for the "buggy" run silently linked against fixed's already-compiled `CategoryPlot.class`, so a test that
genuinely **fails** on real buggy code (confirmed by manually re-running it standalone: exit 1, assertion
failure) was misclassified as passing on buggy -> `VALID_NON_DISCRIMINATING` instead of `VALID_BUG_REVEALING`.
This would have systematically undercounted bug-revealing tests at scale, not just on one example. Fixed by
exporting `dir.bin.tests`/`cp.test` freshly for each of the three workspaces (fixed/buggy/candidate),
immediately after each one's own compile. Re-validated: corrected result matches manual verification exactly.

## Deferred / thin-pass scope
- Only tests whose generated Java parses to exactly one top-level class are supported (`extract_class_name`
  takes the first `class` match). Multi-class or nested-class generated code isn't handled specially.
- No test-generation retry on `INVALID_COMPILE` (a common LLM failure mode); a compile failure is recorded
  as-is, matching the funnel-tracking design (`generated -> syntactically_valid -> compiled -> ...`), not
  silently retried or hidden.
